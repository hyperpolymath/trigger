== Overview

This document describes the architecture for expanding the Trigger application
to support multiple social media platforms beyond Telegram. The design maintains
the existing standards: Ada/SPARK core, Zig FFI with unified-hexadeca-api, and
Idris2 API layer.

== Architecture Principles

=== Separation of Concerns

The architecture follows a strict separation between:

1. **Platform-Agnostic Core** (Ada/SPARK): Business logic that works across all platforms
2. **Platform-Specific Adapters** (Zig + Idris2): Platform-specific implementations
3. **FFI Boundary** (Zig): Safe interface between Ada and external libraries

=== Type Safety

All ABIs (Application Binary Interfaces) are defined in Idris2, providing:

- Dependent types for validation
- Algebraic data types for safety
- Type-level contracts and invariants
- Compile-time proofs where possible

=== Memory Safety

All FFI implementations are in pure Zig, using unified-hexadeca-api for:

- Explicit memory management
- Bounds checking
- Pointer safety with `@ptrCast` and `@alignCast`
- Proper error handling

== Adding a New Platform

To add support for a new social media platform (e.g., Instagram), follow these steps:

=== Step 1: Create Idris2 ABI (API Layer)

Create `ffi/idris2/InstagramAPI.idr`:

[source,idris]

  constructor MkInstagramPost

    allocator: std.mem.Allocator,

    // ... other fields

        // Initialize client
    }
    
    pub fn deinit(self: *InstagramClient) void {
        // Clean up
    }
    
    // Platform-specific methods
    pub fn getProfile(self: *InstagramClient, user_id: []const u8) !void {
        // Implement
    }
};

// C-exported functions for Ada FFI
pub export fn create_instagram_client(token_ptr: [*c]const u8) callconv(.C) ?*anyopaque {
    const allocator = std.heap.page_allocator;
    const token = std.c.toZigString(token_ptr);
    var client = try InstagramClient.init(allocator, token);
    return @ptrCast([*]anyopaque, &client);
}

pub export fn destroy_instagram_client(client_ptr: [*c]*anyopaque) callconv(.C) void {
    const client = @ptrCast(*InstagramClient, @alignCast(@alignOf(InstagramClient), client_ptr));
    client.deinit();
    std.heap.page_allocator.free(client);
}
----

== Platform Interface (SocialPlatform)

The `SocialPlatform` interface in `ffi/idris2/SocialMediaAPI.idr` defines
the contract that all platform implementations must fulfill:

[source,idris]
----
interface SocialPlatform a where
  -- Platform information
  getPlatform       : a -> Platform
  getCapabilities   : a -> PlatformCapabilities
  
  -- Session management
  createSession     : a -> Account -> Effect (Either SocialError Session)
  destroySession    : a -> Session -> Effect (Either SocialError ())
  connect           : a -> Session -> Effect (Either SocialError Bool)
  disconnect        : a -> Session -> Effect (Either SocialError ())
  isAuthorized      : a -> Session -> Effect (Either SocialError Bool)
  refreshSession    : a -> Session -> Effect (Either SocialError Session)
  
  -- Account management
  getAccount        : a -> Session -> String -> Effect (Either SocialError Account)
  listAccounts      : a -> Session -> Effect (Either SocialError (List Account))
  updateAccount     : a -> Session -> Account -> Effect (Either SocialError Account)
  
  -- Message operations
  getMessages       : a -> Session -> String -> Nat -> Effect (Either SocialError (List Message))
  getMessage        : a -> Session -> String -> String -> Effect (Either SocialError Message)
  
  -- Reporting operations
  reportMessage     : a -> Session -> Message -> ReportReason -> String -> Effect (Either SocialError ReportResult)
  reportMessages    : a -> Session -> List Message -> ReportReason -> String -> Effect (Either SocialError (List ReportResult))
  
  -- Platform health
  ping             : a -> Effect (Either SocialError ())
  getRateLimits    : a -> Session -> Effect (Either SocialError RateLimitInfo)
----

== Platform Capabilities

Each platform declares its capabilities through the `PlatformCapabilities` record:

[source,idris]
----
record PlatformCapabilities where
  constructor MkPlatformCapabilities
  
  supportsMessaging     : Bool      -- Can send/receive messages
  supportsReporting     : Bool      -- Can report content
  supportsMultiAccount  : Bool      -- Supports multiple accounts
  supportsSessionPersist: Bool      -- Can persist sessions
  supportsRateLimitInfo : Bool      -- Provides rate limit info
  supportsWebhooks      : Bool      -- Supports webhook notifications
  supportsSearch        : Bool      -- Can search content
  supportsMediaUpload   : Bool      -- Can upload media
  supportsMediaDownload : Bool      -- Can download media
----

The core application uses these capabilities to adapt its behavior:

- If `supportsMultiAccount` is false, hide multi-account UI
- If `supportsSessionPersist` is false, don't save sessions
- If `supportsRateLimitInfo` is true, show rate limit warnings
- If `supportsWebhooks` is true, enable webhook configuration

== Error Handling

All platforms use the unified `SocialError` type for consistent error reporting:

[source,idris]
----
data SocialError = 
  | NetworkError String           -- Network connectivity issue
  | AuthError String             -- Authentication/authorization failure
  | RateLimitError Nat           -- Rate limit exceeded (seconds until retry)
  | NotFoundError String         -- Resource not found
  | PermissionError String       -- Insufficient permissions
  | PlatformError Platform String -- Platform-specific error
  | UnknownError String          -- Unknown/unclassified error
----

Platforms can extend this with platform-specific error types by using
`PlatformError` with their platform identifier.

== Platform-Specific Extensions

Each platform can define its own types and functions beyond the core
`SocialPlatform` interface. These are exported from the platform's module
and can be used by the Ada/SPARK core when targeting that specific platform.

=== Telegram-Specific

- `TelegramSession` - Session with DC (Data Center) information
- `TelegramMessage` - Message with MTProto-specific fields
- `TelegramAccount` - Account with user details
- Functions: `startAuth`, `sendCode`, `signIn`, `getMe`

=== Discord-Specific

- `Snowflake` - Discord's unique ID type
- `Guild` - Discord server
- `Channel` - Discord text/voice channel
- `DiscordUser` - Discord user with discriminator
- `DiscordMessage` - Message with embeds and attachments
- `Role` - Discord role
- Functions: `sendMessage`, `getGuild`, `getChannel`, `getUser`,
  `banUser`, `kickUser`, `addRole`, `removeRole`

=== Twitter-Specific

- `TwitterId` - Twitter user/tweet ID
- `TweetId` - Tweet identifier
- `TwitterUser` - User with followers/following counts
- `Tweet` - Tweet with metrics
- `TweetAttachment` - Media attachment
- Functions: `postTweet`, `getUserTimeline`, `getHomeTimeline`,
  `retweet`, `likeTweet`, `followUser`, `blockUser`, `muteUser`

== Rate Limiting

Each platform has its own rate limiting characteristics:

| Platform   | Rate Limit Window | Requests | Notes |
|------------|-------------------|----------|-------|
| Telegram   | 1 second          | 30       | Per DC |
| Discord    | 1 second          | 50       | Per guild |
| Twitter    | 15 minutes        | 300      | Per endpoint |
| Instagram  | 1 hour            | 200      | Per token |
| Reddit     | 10 seconds        | 60       | Per endpoint |

The Zig FFI layer includes rate limit management utilities in
`ffi/zig/social_media/common.zig`:

- `RateLimitState` - Tracks rate limits per endpoint
- `shouldWait` - Check if should wait for rate limit
- `updateLimit` - Update rate limit for an endpoint
- `getRemaining` - Get remaining time for an endpoint

== Authentication

Each platform uses its own authentication mechanism:

=== Telegram

- Uses MTProto 2.0 authorization
- Requires `api_id` and `api_hash` from my.telegram.org
- Phone number verification with SMS/code
- Session files for persistence

=== Discord

- Uses OAuth 2.0 with Bot or User tokens
- Bot tokens: `Bot <token>`
- User tokens: `Bearer <token>`
- Requires specific scopes/permissions
- Token revocation via `/revoke`

=== Twitter

- Uses OAuth 2.0 Bearer Token (for app-only auth)
- Or OAuth 1.0a (for user auth)
- Requires Developer Portal app creation
- Scopes: `tweet.read`, `tweet.write`, `users.read`, etc.

The `AuthTokens` struct in `common.zig` provides a standard format:

[source,zig]
----
pub const AuthTokens = extern struct {
    access_token: []const u8,
    refresh_token: []const u8,
    expires_in: u64,  // seconds
    token_type: []const u8,
};
----

== Security Considerations

=== Token Storage

- All access tokens should be encrypted at rest
- Use platform-specific encryption (AES-256 for Telegram sessions)
- Never log tokens or sensitive data

=== Rate Limiting

- Respect platform rate limits
- Implement exponential backoff on 429 responses
- Use separate rate limiters per endpoint/platform

=== Error Handling

- Never expose platform-specific error details to users
- Sanitize error messages before logging/displaying
- Implement retry logic with jitter for transient errors

=== Input Validation

- Validate all platform IDs (Snowflakes, Twitter IDs, etc.)
- Sanitize all user input before sending to APIs
- Validate message lengths against platform limits

== Testing Strategy

Each platform implementation should include:

1. **Unit Tests**: Test individual functions in isolation (Idris2)
2. **Integration Tests**: Test FFI bindings (Zig)
3. **E2E Tests**: Test complete workflows (Ada/SPARK)
4. **Mock Tests**: Test with mocked API responses
